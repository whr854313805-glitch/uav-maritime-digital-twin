# F28：删除重复刷新流程，统一结果与目录

原问题：合法新latest已发布，工作台catalog还保存旧哈希，自检报Workspace is stale for current。本轮不改规划算法/参数，不删校验，不改船位或冻结点。

## 已整理的同类问题

- 默认结果只走共享发布入口：检查成功语义/来源/请求，再更新latest、派生目录及provenance。原CLI解析失败的缺字段latest直接覆盖分支已删除。
- 启动、准备、读取、完整自检使用同一同步逻辑。只允许合法current元信息更新；冻结目录条目、船位、八点、锚点、地图边界或背景不符仍报错。已验证的失败结果可显示；来源未验证的错误不能发布为默认。
- 计算完成但发布失败时，计算结果保持原状态，另存publication_error.json并向调用方报错，避免同一run_id在默认结果中成功、在运行记录中却被改写为求解失败。
- 多个发布者、读取与准备共享项目文件锁，最多等20秒后明确失败。每份JSON原子替换；不宣称三个文件是一次磁盘事务。发布已完成但目录/来源写入中断时不报成功，下一次读取/启动从合法新结果补齐派生信息，不丢新结果。
- 已移除“刷新已保存数据”按钮及重建背景的手动刷新分支。原生界面每约1秒发现目录变化，当前显示默认结果时自动重新加载；有手动输入的出发时间不自动覆盖。20秒/1秒是工程等待/显示轮询设置，不是规划或安全参数。
- 没有变化就不写文件；目录更新不重画背景。JSON写盘失败会清理本次临时文件。保留16个有来源的保存入口和必要历史证据，不将其误当垃圾删除。

## 证据

- 68项自动化测试（原52＋新增16）通过。新增包括连续三次发布、双进程发布、锁等待上限、来源/投影/语义错误拒绝、合法失败显示、两处写盘中断恢复、无变化不重写、旧目录自动补齐、CLI坏请求不覆盖默认和失败临时文件清理。
- 实际AnyLogic中两次通过原run_task新算M2，再发布默认结果：当前画面均自动重载到新run_id，9项自检通过，bootstrap保留新结果并保持目录与provenance一致。测试后原latest/workspace/provenance逐字节恢复。见native-publication.json；这不是模拟更换run_id来冒充新实验。
